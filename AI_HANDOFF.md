## 1. Пользователь и правила общения

Пользователь не является разработчиком и раньше не занимался подобными проектами.

Нужно:

- писать по-русски и очень простыми словами;
- не использовать технические термины без расшифровки;
- каждый пункт запроса отвечать отдельно;
- действия пользователя описывать пошагово: что открыть, куда нажать, что должно появиться;
- не заставлять пользователя повторять длинную операцию без крайней необходимости;
- перед выдачей новой версии самостоятельно запускать тесты и сборку;
- прямо признавать ошибки и объяснять, что именно исправлено;
- не просить пользователя присылать секреты, cookies, пароли, токены или коды доступа;
- не просить пользователя вручную менять код блоками; если понадобится ручная замена, давать полный файл;
- после законченного этапа сохранять изменения в Git и оставлять короткий итог.

## 2. Главная идея проекта

Нужен бесплатный локальный помощник для личного мониторинга форумов, начиная с темы 4PDA:

<https://4pda.to/forum/index.php?showtopic=1108618>

Пользователь вручную открывает любую страницу темы и нажимает кнопку расширения. Расширение должно:

1. определить сообщения на странице;
2. найти последнюю страницу темы;
3. пройти назад до сохранённой точки отсчёта;
4. добавить только новые сообщения без повторов;
5. сохранить текст, автора, дату, ссылки, цитаты, изображения и связь с сообщениями, на которые отвечают;
6. подготовить материалы для ручной передачи в онлайн-ИИ;
7. принять ответ ИИ;
8. сохранить читаемую выжимку и структурированные Q&A локально.

ИИ не вызывается автоматически. Пользователь сам решает, какой файл передавать онлайн-ИИ.

## 3. Жёсткие ограничения

Нельзя:

- обходить CAPTCHA, 403, 429, логин, robots.txt и ограничения сайта;
- использовать прокси-ротацию, маскировку автоматизации или обход rate limit;
- автоматически отправлять запросы в веб-интерфейс ИИ;
- автоматически читать ответы веб-интерфейса ИИ;
- коммитить cookies, логины, токены, личные данные и диагностические логи с приватными URL.

При CAPTCHA, логине, 403 или 429 сбор должен остановиться с понятным сообщением.

### Сбор сообщений 4PDA

По диагностическому логу пользователя установлено:

- настоящие тела сообщений: `div.postcolor[id^="post-"]`;
- количество тел на странице было 21;
- имена пользователей: `.normalname`;
- информация пользователя: `.postdetails`;
- блоки спойлеров: `.post-block.spoil.close`;
- служебная разметка имела `id`, начинающиеся с `post-`, поэтому старый алгоритм ошибочно сохранял меню как сообщения.

Текущий адаптер должен брать `postcolor` как тело сообщения, а метаданные искать в строке сообщения и в `#post-member-<postId>`.

### AI-файлы

В разделе 3 popup есть два режима:

1. **Скачать одним файлом для ИИ**
   - можно поставить одну или несколько галочек: Markdown, JSON, TXT;
   - каждый выбранный файл содержит промпт, требования к ответу и все сообщения;
   - JSON дополнительно содержит структурированные поля.

2. **Скачать с разбивкой на части**
   - используется только для очень больших объёмов;
   - создаёт prompts `fkb-prompt-01-of-N.md` и другие JSON-файлы;
   - создаёт `fkb-combine-prompt.md` для объединения ответов частей;
   - создаёт `fkb-full-posts.txt` для архива.

В prompt ИИ требуется вернуть:

- валидный JSON схемы 1.0;
- полноценную читаемую Markdown-сводку без воды в поле `markdown_summary`;
- при желании тот же текст отдельным блоком после строки `---MARKDOWN---` — импорт принимает оба варианта;
- важные новости, решения, проблемы, слухи, ссылки, проверки, Q&A и конфликты;
- URL исходных постов для значимых утверждений.

С версии `0.3.3` в prompt вшиты (файл `extension/src/core/prompt.ts`):

- заполненный шаблон ответа: все поля с примерами значений, чтобы модель копировала форму, а не придумывала её;
- список правил формата, которые модели нарушают чаще всего: `report.conflicts` — массив строк,
  URL без Markdown-обёртки и без `&amp;`, `status` только из значений схемы, пустые списки — `[]`,
  без полей вне схемы, без текста до и после JSON.

### Импорт ответа ИИ

Файл: `extension/src/core/importer.ts` (такая же логика продублирована в
`companion/fkb_companion/parser.py`, оба варианта должны меняться вместе).

Порядок обработки ответа:

1. найти первый JSON-объект;
2. привести его к схеме 1.0 (`normalizeAiAnswer` / `_normalize_ai_answer`);
3. строгая проверка;
4. если не прошло — добавить пропущенные поля и проверить снова;
5. если и это не помогло — сохранить хотя бы читаемую Markdown-сводку.

Шаг 2 появился после реальной ошибки пользователя и исправляет то, что модели делают постоянно:

- `report.conflicts` объектами `{title, description, source_post_urls}` вместо массива строк —
  превращаются в строки вида «Заголовок — описание (источники: URL)»;
- ссылки в Markdown-обёртке `[https://...](https://...)`, в угловых скобках, с `&amp;` и
  с текстом вокруг — очищаются до обычного URL;
- статусы словами («подтверждено», «не подтверждено», «устарело») — к значениям схемы;
- поля вне схемы — убираются с предупреждением, исходный ответ остаётся в `raw_ai_response`;
- `markdown_summary` (или алиасы `summary`, `markdown`) — расшифровываются HTML-сущности.

Импортёр:

- извлекает первый JSON-объект из полного ответа;
- отделяет Markdown после `---MARKDOWN---`;
- принимает отсутствующие необязательные поля;
- восстанавливает `null` в полях, где ожидается строка или массив;
- превращает одиночную строку ссылки в массив;
- добавляет пустой `report.conflicts`;
- добавляет отсутствующие статусы как `unconfirmed`;
- переносит Q&A из Markdown, если в JSON Q&A нет;
- сохраняет человекочитаемую Markdown-сводку в поле `parsed_summary`;
- сохраняет полный исходный ответ в `raw_ai_response`;
- сообщает, что JSON был автоматически восстановлен.

Важное исправление для последней ошибки пользователя: тесты должны покрывать не только пропущенные поля, но и значения `null` и одиночные строки.

### Локальная база

Основные IndexedDB stores:

- `sources`;
- `posts`;
- `runs`;
- `reports`;
- `qa`.

Есть действия:

- **Удалить только неправильные записи** — удаляет очевидное меню и испорченную кодировку, оставляет точку отсчёта;
- **Удалить данные этой темы и начать заново** — удаляет посты, отчёты, Q&A и checkpoint выбранной темы;
- **Удалить всю базу расширения** — удаляет все темы, посты, отчёты и Q&A;
- **Скачать всю базу для редактора** — выдаёт JSON и Markdown без AI-промпта.

Перед опасным удалением должно быть подтверждение.

## 6. Последняя проблема пользователя и её причина

Пользователь сделал полный сбор примерно 20 страниц форума, отдал пакет онлайн-ИИ и
импортировал ответ обратно. Расширение ответило «Сохранена Markdown-сводка. Распознано Q&A: 0»,
то есть структурированный отчёт потерялся.

Причина найдена и подтверждена на реальном ответе пользователя (проверено тестом
`extension/tests/fixtures/ai-answer-2026-09.json`):

```text
report.conflicts должен быть массивом строк.
```

Онлайн-ИИ вернул `conflicts` как массив объектов `{title, description, source_post_urls}`,
а схема 1.0 требует массив строк. Одно это поле отклоняло весь JSON, поэтому:

- Q&A из JSON не сохранялись;
- сводка тоже терялась, потому что ИИ положил её в поле `markdown_summary` внутри JSON,
  а не отдельным блоком после `---MARKDOWN---`, и в базу записывался сырой JSON.

Дополнительно все ссылки пришли в виде `[https://4pda.to/...&amp;st=13260](https://...)`,
то есть были некликабельны.

Всё это закрыто в версии `0.3.3` (см. раздел «Импорт ответа ИИ»). При следующем обращении
пользователя **нельзя просить его повторно собирать страницы**: нужно попросить установить
`extension/dist` версии `0.3.3` и заново импортировать тот же самый файл с ответом ИИ.

Ожидаемый результат импорта:

- `JSON сохранён после автоматического заполнения пропущенных полей. Q&A-карточек: 5.`;
- в предупреждениях видно, что именно исправлено:
  `report.conflicts: 2 объект(а) заменены на строки.` и
  `Ссылки очищены от Markdown-обёртки и HTML-экранирования: N шт.`;
- в разделе **7. Сохранённые выжимки** — читаемая Markdown-сводка, а не JSON.

Если пользователь всё ещё получает старые ошибки, первым делом попросить проверить внизу popup
версию `0.3.3`. Если там старая версия — браузер загружает старую папку `extension/dist`.

### Вторая проблема пользователя: период «замерзал» на 31 августа

Пользователь удалил базу, заново собрал сообщения, а ИИ снова показал
`"period": {"from": "2026-03-08...", "to": "2026-08-31T15:52:00.000Z"}`, хотя на форуме уже
были сообщения от 2 сентября.

Причина подтверждена проверкой на реальной разметке темы 1108618
(<https://4pda.to/forum/index.php?showtopic=1108618>, 682 страницы, последняя `st=13620`):
4PDA печатает даты как `DD.MM.YY, HH:MM`, например `10.07.25, 11:09`, а `parsePostedAt`
отдавал эту строку в `Date.parse`. В движке V8:

```text
Date.parse('02.09.26, 09:30') -> 2026-02-09   (вместо 2 сентября — 9 февраля)
Date.parse('08.09.26, 12:00') -> 2026-08-09   (вместо 8 сентября — 9 августа)
Date.parse('31.08.26, 23:52') -> NaN          (не распознано)
```

Поэтому сентябрьские сообщения получали даты января и февраля, сортировка и период в промпте
съезжали, а «новыми» выглядели августовские посты. Новые сообщения при этом скачивались —
просто с неверными датами.

Исправлено в `0.3.4`: собственный разбор дат (`parseForumDate` в `extension/src/core/utils.ts`),
день.месяц.год, поддержка `Сегодня/Вчера`, дат с названием месяца и ISO; штамп поста берётся
первым совпадением в строке, чтобы не подхватить «Регистрация: 01.01.24» или отметку о правке.

### Третья проблема пользователя: «много строк „Дата: не распознана“»

После пересбора в файле для ИИ у части сообщений стояло «Дата: не распознана».
`Дата: не распознана` означает, что `posted_at` пуст, то есть дата не нашлась **в тексте**
того блока, который адаптер считал строкой сообщения. В классической табличной разметке 4PDA
дата лежит в той же `<tr>`, а в более новой — в шапке, которая является **соседом** тела
сообщения внутри общего контейнера. Старый код смотрел только в один корень
(`dateRoot || metadataRoot`), поэтому такие сообщения оставались без даты.

В `0.3.5` `parsePostedAt` принимает список корней (`dateCandidateRoots` в
`extension/src/adapters/dom.ts`) и перебирает их от узкого к широкому:
ячейка `td#post-main-*` → `<tr>` → родители (не выше 4 уровней и только пока в родителе
одно тело сообщения) → сам блок. Благодаря проверке «одно тело сообщения» дата соседнего
поста не подхватывается.

Если дата всё равно не найдена, адаптер пишет в диагностику:
`4PDA: у N сообщений не найдена дата. Начало первого блока страницы: «…»`.
**Если пользователь снова увидит «Дата: не распознана», первым делом попросить прислать эту
строку из диагностики** — в ней видно реальную разметку, и по ней можно добить селекторы,
не заставляя пользователя собирать данные заново.

Пустые даты влияют на результат: такие сообщения не попадают в период, сортируются по номеру
поста и ИИ хуже понимает, что из них новое.

### Что добавлено в интерфейс в 0.3.5

- «Загрузить страницы от открытой» — для анализа страниц **до** точки отсчёта: пользователь
  открывает нужную старую страницу темы и нажимает кнопку, сбор идёт назад от неё
  (флаг `fromOpenPage` в `messages.ts` → `background.ts` → `collector.ts`, при нём последняя
  страница темы не ищется).
- «Свернуть все разделы» в разделе 7 — сворачивает все `details` внутри списка выжимок.
- Одинаковые пункты из разных разделов объединяются при показе (см. `groupSections` в
  `extension/src/core/report-view.ts`).
- Повторный импорт того же ответа ИИ не создаёт вторую копию: `background.ts` сравнивает
  `raw_ai_response` с уже сохранёнными отчётами источника и возвращает `duplicate: true`.

Проверить глазами после обновления: в диагностике сбора появились строки
`Собрано страниц: N.` и `Сообщений в базе после сбора: N. Период сообщений: … — …`.
Если верхняя граница периода снова не совпадает с последней страницей темы — значит, проблема
уже в другом месте, и нужен диагностический лог последней страницы.

## 9. Git и доставка

Работать только в ветке:

```text
arena/01a060b9-web-site-anaclitic
```

Не создавать и не использовать другие ветки.

Готовая папка `extension/dist` намеренно хранится в Git, чтобы пользователь без разработки мог загрузить расширение в Chrome/Edge.

Не коммитить:

- `node_modules`;
- `.venv`;
- `companion/data`;
- SQLite-файлы пользователя;
